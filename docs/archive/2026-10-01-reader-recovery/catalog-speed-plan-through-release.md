# План быстрого каталога — 25 сентября 2026

Цель: при входе быстро получить актуальные названия и порядок книг с сервера, затем заполнить карточки локальными данными и асинхронными обложками. При недоступности сервера — ограниченное ожидание, сохранённая библиотека своего аккаунта, уведомление и повтор. Корректность Recently Read между устройствами и после возврата из Reader входит в результат.

Исходная реализация v2 была разрешена пользователем; проверки и риски записаны перед её изменением. 26 сентября пользователь разрешил push/deploy бэка и миграцию рабочей БД после тестов при наличии отката; dev целиком переведён на новый frontend. Production frontend переключается после dev-приёмки. **Оптимизации реализованы локально и прошли первоначальную проверку. Теперь пользователь запросил расширенную проверку перед production, включая закрытие пробела с реальными EPUB.** Детальный [контракт библиотеки](../../../reference/architecture/library-contract-as-is-to-be.md), прежде всего последние уточнения раздела 1, остаётся источником требований; безусловный cache-first и opt-in в старый `/api/books` не применяются. Уточнение 26 сентября допускает короткое повторное использование подтверждённого полного индекса по D14.

## Принятые ограничения

1. Новые маршруты, начиная с `GET /api/v2/library`; старые `/api/books` handlers, JSON/NDJSON и используемые другими клиентами write-контракты остаются без изменений. Новые service/helper файлы не должны незаметно менять legacy поведение.
2. В новом frontend один загрузчик каталога и один формат кеша. Нет постоянного feature flag между двумя API, runtime возврата к тяжёлому legacy списку или параллельных сортировщиков. Dev целиком переходит на новый frontend; после его приёмки production целиком переходит на новый frontend.
3. В пределах короткого кулдауна D14 допустим сразу полный недавно подтверждённый индекс своего scope. Вне этого исключения на входе сначала skeleton; кеш виден при timeout/сетевом сбое. После успешного ответа локальные изображения заполняют подтверждённые сервером карточки. Временный placeholder собственной текущей загрузки по D13 не означает подтверждение полного индекса.
4. Сервер определяет разрешённый набор и порядок. Возврат из Reader не публикует индекс, который ещё не учитывает предшествующее чтение/мутацию этого клиента. Нужен ack или эквивалентная гарантия read-your-writes в пределах общего срока ожидания.
5. Оригинальные книги, обложки, несинхронизированные позиции, пользовательские данные и legacy поля не удаляются. Подготовка thumbnails и возможные новые поля/таблицы аддитивны. Не выполнять blanket reset IndexedDB/localStorage.
6. Длинные snapshot-сессии, новый общий offline sync engine и пагинация не являются обязательным стартовым объёмом. Выбирать их только для измеренной проблемы; минимальная обработка pending reading activity обязательна до переключения frontend.

## Этап 0. Ограничить критический путь и выбрать масштаб

Вопрос: сколько нового ожидания создают identity, БД, сериализация, proxy и собственно передача компактных данных? Снять отдельные timings прямого backend и полного browser → proxy → backend пути в согласованной тестовой среде. Проверить установленную схему/индексы, effective visibility и все источники recency; исходники миграции не доказывают её применение.

Начать с guest, обычного authenticated аккаунта и библиотеки большего размера. Зафиксировать scope без токенов, число книг, сеть/устройство, cold/warm, ошибки, размер ответа, время названий и реально показанных обложек. Не собирать private titles/содержимое книг в общие логи.

**Первый вариант — полный компактный manifest:** все разрешённые ID, названия/авторы, effective status/права, canonical recency и thumbnail references/versions, без изображений и глав. Полнота ответа явная; одна согласованная server projection задаёт порядок. Не наследовать нынешний recency-head + created-at-tail. Для обычного размера такой ответ проще cursor/snapshot инфраструктуры. Рендер первых шести и загрузка их картинок не ждут картинок остальных книг.

Предварительная граница проверки — 1000 книг и не более 512 KiB декодированного manifest. Это экспериментальный предел, не установленный лимит продукта: проверить также реальный крупный аккаунт, если он доступен. Если полный manifest укладывается в бюджет, сохранить его и клиентскую работу по полному набору для поддерживаемых фильтров/поиска. Если превышает размер или время, назвать конкретную причину и перейти к серверным sort/filter/limit; не обрезать массив без continuation. Не грузить все cover blobs или все тяжёлые metadata в Node ради отбора первых книг.

Ожидаемое доказательство: короткая таблица timings/bytes, план SQL/EXPLAIN на тестовых данных и выбранная стратегия перечисления. Бюджет: до 3 диагностических запросов на каждый из 3 scopes; для проверки масштаба одна изолированная fixture-библиотека на 1000 книг и один диагностический SQL plan. При auth/schema blocker остановить соответствующее измерение, не заменять его гостевым результатом. Не создавать массовые production записи ради benchmark.

## Этап 1. Новый компактный серверный путь

- Новый route/service и отдельный frontend proxy route. Explicit account/share context обязателен: существующий share helper работает только с префиксом `/api/books`. Подтвердить principal; не выдавать guest success вместо ожидаемой пользовательской библиотеки.
- Новый DTO явно задаёт contract version, scope/query context, revision, полноту и items. В SELECT и wire payload нет оригинального base64. Название/автор, ID, effective status, права и данные порядка доступны без дополнительных запросов; reading summary batch/join допускает unknown, если честный процент недоступен. Не вызывать N reading-position GET ради карточек.
- Глобальный Recently Read сортируется до выбора head/страницы: каноническая recency, затем deterministic ties. Выбрать и проверить null/unread правило, created_at/ID tie-break и title collation. Legacy language PATCH и старые writers сейчас загрязняют last_read_at: простое переименование поля не создаёт событие чтения.
- При полном manifest один запрос получает согласованный набор; если серверные чтения составные, проверить отсутствие смеси разных membership/order состояний. Revision — сигнал изменения, не обещание исторического snapshot. Не заводить хранение snapshot-сессий для одного малого ответа.
- При обоснованной пагинации сервер применяет доступ, visibility, поиск и выбранную сортировку ко всему набору до limit. Cursor привязан к scope/query. До выпуска выбрать фиксированное перечисление либо обнаружение смены revision с явным restart; второе не называть snapshot. Не смешивать страницы разных revision; partial cache не обозначать полной библиотекой.

Выход этапа: новый endpoint отдаёт лёгкий корректный индекс; unchanged legacy запросы дают прежний контракт. Это подготовка, ещё не законченный пользовательский путь.

## Этап 2. Подтверждённое чтение и отдельные thumbnails

**Reader → Library:** определить минимальное новое activity событие реального готового Reader/чтения и добавить отдельный write endpoint, если существующих подтверждений недостаточно. Event ID, scope и исходное время сохраняются до ack; повтор не создаёт новое чтение. До показа индекса дождаться ack влияющих на него действий и читать не старше подтверждённой версии, либо получить равнозначную атомарную операцию. Барьер входит в общий timeout. Failed/delayed ack ведёт к scoped fallback с pending локальным порядком; более старый server order не показывается как промежуточный успех.

Не превращать position conflict в максимум номера страницы: чтение назад допустимо. Существующее `persisted:false` остаётся отличимым от успешного HTTP. Новое событие чтения и версия позиции — разные сущности. До переключения принять конкретную политику часов, delayed offline событий и logout; хотя общий offline engine отложен, pending activity не должна бесследно теряться при перезагрузке. Не обещать replay всех offline мутаций, которых текущий клиент не умеет доставлять.

Для двух устройств новый канонический порядок строится из одного серверного источника. Проверить всех legacy writers и выбрать совместимую projection/дополнительное поле, не изменяя старые handlers и общую семантику молча. Старые last_read_at без provenance можно использовать только как явно обозначенное legacy приближение; историческое реальное чтение из них не восстановить. Зафиксировать границу строгих гарантий для нового и legacy клиента до реализации.

**Обложки:** новый import/backfill шаг создаёт маленький thumbnail и хранит размер/version отдельно от оригинала; list GET ничего не декодирует и не ресайзит. Backfill возобновляемый и ограниченный, с первоначальной пробой на 6 книгах. До больших записей оценить свободное место, рост и сохранность оригиналов. Отсутствие thumbnail не блокирует названия: отдельный разрешённый image URL/placeholder — переходный вариант, но передача оригиналов не считается достижением thumbnail бюджета.

Private image endpoint/signed URL сохраняет доступ; public bucket не является универсальным решением. Ключ изображения — scope + book ID + thumbnail version. Истечение URL обновляет доступ к картинке, а не меняет весь каталог. Декодирование/ошибка изображения не меняет порядок и не переводит всю библиотеку в offline. Обложки догружаются самостоятельной ограниченной FIFO-очередью сверху вниз в порядке полки. Приоритеты и перестановки по viewport исключены пользователем; скролл не запускает и не переупорядочивает сетевую очередь. Готовый ответ заполняет свой слот независимо от завершения предыдущих картинок.

Сохранить legacy `/sync/status` даты и EPUB binary/Content-Disposition поддержку proxy, пришедшую из main.

### Локальная среда и границы изоляции

При составлении плана установлено: обычный backend launcher `.local/dev.mjs` читает `.env` с production Supabase, поэтому для этих испытаний **не используется**. Есть отдельный PostgreSQL 15.18 с синтетическими SQL fixtures в backend `.local/catalog-v2-pg`, standalone Nitro harness с loopback Supabase-ответами и frontend fixture server. SQL fixtures упрощают `auth.users`/`auth.uid()`; Nitro stub не является настоящим Auth/PostgREST. Тогда полного local Supabase Auth ещё не было; Docker, Supabase CLI и альтернативный контейнерный runtime в проверенных местах не обнаружены. В ходе реализации отдельно подняты native Auth v2.197.0, PostgREST16.4 и PostgreSQL15.18 с собственными ключами. Docker/полный Supabase Storage не устанавливались; их покрытие не заявляется.

Минимальная подготовка стенда:

1. Переиспользовать существующие изолированные QA-копии, сверив их source revision. Не копировать рабочие `.env`, ключи, cookies, пользовательские БД или production dump. Передавать дочернему процессу явный небольшой набор env; проверить отдельно build-time `NEXT_PUBLIC_*` и runtime `API_URL`/Supabase, поскольку frontend URL может уже находиться в собранном JS. Пользовательские рабочие файлы не править ради запуска тестов.
2. Выделить свободные loopback-порты и отдельные тестовые данные. Launcher принимает только ожидаемые local origins/DB host и завершается с ошибкой при другом адресе **до подключения**. Негативная проверка конфигурации использует заведомо недопустимый тестовый адрес, без запроса к production. Браузерные fixtures используют отдельный тестовый origin/context без переноса рабочей сессии; пользовательские cookies/IndexedDB не очищаются. Существующие пользовательские процессы/Redis не останавливать.
3. Для unit/HTTP fixtures запретить внешние назначения в тестовом transport; неизвестный HTTP method/path — явный FAIL, а не универсальный успешный `[]`. Подставляются время и внешние ответы, но настоящие controller/middleware/SDK adapters остаются исполняемыми. Проверять и ошибочный ответ, чтобы fixture не гарантировал успех сам по себе.
4. Для integration process не задавать Redis; EPUB/cost workers не должны стартовать. LLM, платежи, email и аналитика идут только в локальный stub/отключаются в тестовой конфигурации. У backend PostHog есть fallback key, поэтому простого удаления env недостаточно: указать локальный sink и проверить адреса/выходные вызовы. Передавать production credentials через тестовый transport не требуется.
5. Для настоящего refresh/login/logout отдельно подготовить local Supabase Auth + PostgREST + PostgreSQL с собственными ключами и синтетическими аккаунтами. Это единственная новая инфраструктура, обоснованная HTML/session правкой. До установки проверить требуемые образы/место; если поднять её нельзя, R09/R10 остаются непроверенными и HTML-правка не входит в готовый выпуск. Первые две правки можно продолжать проверять существующими средствами. Альтернатива — отдельный non-production Supabase project, но это уже облачная проверка и отдельное изменение среды, не скрытая замена локального стенда рабочей базой.

Защита опирается на отсутствие рабочих credentials, проверенные адреса и ограниченный transport. Сейчас **не заявляется системный firewall/sandbox**, перекрывающий все исходящие соединения процесса: env-подмена такого доказательства не даёт. Для этого небольшого изменения не строить отдельную платформу сетевой изоляции; сначала проверить реальные настройки и вызовы используемых процессов. Никакие новые стенды в ходе составления плана не запускались.

Удаление ожидания `getUser()` без доказанного пути обновления cookies не является готовой оптимизацией. Успешный первый экран на свежем токене этого не проверяет.

### Размер проверки без избыточного стенда

- Сначала существующие средства: два synthetic пользователя, guest, два share scope, 18 карточек с public/private/hidden/empty cases и одна плохая обложка. Сохранять отдельные edge-case tests; не перемножать все измерения в сотни одинаковых браузерных прогонов.
- На каждую правку — её целевые regression tests. После объединения — один полный детерминированный suite и production build каждого изменённого приложения. Повторять полный цикл только после изменения кода, существенной конфигурации или найденного сбоя; SQL/1000-book/image stress не запускать заново без изменения соответствующего слоя или названной гипотезы.
- Сначала 3 smoke изменённого пути, затем одна bounded сравнительная серия по бюджетам ниже. Обычные функциональные ошибки исправлять до расширения benchmark. Массовые production записи и платные LLM-задачи не нужны.
- Перед setup/build измерить свободное место и ожидаемый размер образов/выходов. На момент проверки свободно около 18 GiB; существующие QA frontend/backend/PG занимают примерно 662/66/72 MiB. Переиспользовать их, не копировать node_modules. Чистить только подтверждённые собственные временные результаты; новый основной отчёт/логи держать в пределах 5 MiB, полные HAR/private payload не собирать. Native Auth/PostgREST/PG стенд занял около 204 MiB; Docker не понадобился. Новые основные evidence пока меньше 0,5 MiB.
- Не добавлять глобальный auth cache, новую очередь, общий sync engine, миграцию БД, постоянные дубли API или observability-платформу. Для доказательств достаточно существующих test traces и нескольких timing/count marks без секретов. Сокращение региона — отдельный следующий эксперимент, если штатный свежий индекс после этих исправлений всё ещё не принят по скорости.

### Порядок выполнения после согласования реализации

1. **Подготовить изолированную среду.** Выполнить проверки env/адресов/сборочной копии из раздела выше. Получить отрицательный тест «чужой адрес отвергнут до сети». Существующий prod-connected launcher не запускать. Зафиксировать, какие процессы настоящие и какие подставлены; не выдавать два раздельных unit слоя за уже проверенный сквозной HTTP→Auth→SQL путь.
2. **Зафиксировать baseline и воспроизведение.** Commits/runtime/config, ответы и порядок на synthetic данных, количество внешних вызовов, существующие PASS/FAIL. Новые тесты воспроизводят зависший cache gate и дополнительные Auth/profile ожидания до исправления; не подгонять fixtures под новый код. Исторический PASS не заменяет проверку исходной ревизии.
3. **Исправить cache gate.** Отдельный commit; R01–R04, соответствующие Reader/мутации/FIFO tests и реальный браузер с IndexedDB. Не менять свежесть, предел ожидания, порядок ACK и способ хранения. Результат: здоровый онлайн-запрос не ждёт непригодный кеш, offline поведение и пригодный cooldown сохранены.
4. **Исправить v2 Auth/IP.** Отдельный commit; middleware→handler тесты R05–R08/R12 и standalone Nitro. Перенести смысл 13 исследовательских пар в постоянный suite с правильным ожидаемым blocked-email outcome. Проверять настоящий request lifecycle с медленным локальным profiles endpoint; не ограничиваться mock вызова fire-and-forget helper. Существующие API вне v2 сохранить.
5. **Проверить и оптимизировать HTML/session.** Подготовить настоящий local Auth, кратко зафиксировать путь token refresh/cookie write, затем отдельный commit с R09/R10. ### Измерение выигрыша, стоп и откат

Сравнивать одну библиотеку, аккаунт, сеть и устройство до/после, отдельно: guest/auth; первый вход/повтор; свежий/истёкший receipt; hard reload/Reader return; готовый/pending ACK. Начало навигации → HTML → controller → GET dispatch → headers/body → названия → первые обложки. Сервер отдельно: Auth count/time, blocklist, profile wait и RPC. Зафиксировать порядок ID и наличие GET до timeout; не выводить private titles/tokens/cookies в traces. Протокол и численные цели ниже остаются действующими; исправление R01 само по себе не обещает нужной полной скорости при Oregon.

Успех отдельных правок определяется также механизмом: R01 запускает GET до ответа зависшего диска; R02 не продлевает срок и сохраняет 0 GET при пригодном кеше; R05 делает ровно один live Auth на bearer request и проверяет заново следующий request; R07 не ждёт profile write. Эти признаки проверяются управляемыми promises/clock, без хрупкого требования «локальный тест обязательно меньше 1 мс». Общий эффект требует сопоставимого browser benchmark. Небольшая серия не доказывает production p95; timeouts и неблагоприятные случаи не исключаются из результата.

**Стоп:** любая чужая карточка/обложка, guest downgrade, обход blocklist/ACL, потеря reading event/позиции, неверный порядок после ACK, сломанное session renewal/login, переставший работать действующий endpoint; также новый timeout или превышение согласованного бюджета. Новый обязательный тест FAIL/NOT RUN блокирует утверждение готовности соответствующего изменения. Целевые PASS плюс build без R09/R10 не разрешают считать HTML/session правку проверенной.

Откат готовится до публикации: сохранить точные предыдущие frontend и backend deployment IDs/commits и настройки. Текущий baseline dev `3af5dbe` (`dpl_82A1BuqtsnPdC9YZNNjngvrdpdN6`), backend `fb6786d` (`dep-darvddvf3r2c73afgmr0`); перед будущим rollout повторно сверить их фактическое состояние. Фронтовую часть возвращать предыдущим deployment/alias, backend — предыдущим artifact. Схема БД не меняется, SQL rollback и очистка пользовательских кешей не требуются; новых несовместимых cache formats не вводить. После возврата проверить вход, полку и Reader. Если части оказались связанными, вернуть согласованную предыдущую пару; не оставлять непроверенную комбинацию.

## Как проверяем: хороший и плохой результат

**Хороший результат:** все обязательные проверки корректности ниже прошли; старые серверные handlers сохранены; полный новый путь реально показывает нужные названия и обложки в заявленных бюджетах. Сравнимый cold median должен ускориться хотя бы вдвое против baseline; p95 также должен укладываться в цели выше. Это критерий приёмки, не уже полученный результат. **Плохой результат:** любое нарушение identity/данных/порядка, потеря pending события, скрытая неполнота списка, повторная публикация устаревшей попытки; либо ускорение только пустого skeleton/текста при медленных обложках. Превышение performance budget или неподтверждённое реальное поведение означает «нужно доработать/проверить», а не PASS.

Синтетические проверки доказывают только заданные сценарии. Отсутствующая authenticated/cross-device или реальная performance проверка явно остаётся NOT RUN и блокирует утверждение о готовности выпуска; guest/mock нельзя подставлять вместо неё. При изменении бюджета сначала записать измеренную причину/компромисс в D06; не ослаблять критерий только ради зелёного отчёта.

### Исходные замеры и предварительный региональный вариант, 26 сентября

Скорость текущего dev не принята. В ограниченных пробах warm HTTP индекса: guest 521 мс напрямую Render / 541 мс через Vercel, authenticated 1052 / 1054 мс; получение тела после headers 0,2–11,2 мс. Чистый SQL: первый guest 97,600 мс и следующий auth 6,544 мс; разные запросы, не парное доказательство cold/warm. Это не p95. [HTTP и разбор](evidence/dev-latency-breakdown.json), [EXPLAIN](evidence/dev-latency-sql-explain.txt).

Причины: Render Oregon, Vercel iad1, Supabase Ireland; последовательные remote auth/RPC, иногда дополнительно блокирующий track-IP. Вопрос следующего эксперимента: насколько размещение backend в Европе сокращает usable-index без изменения membership/auth семантики. До пяти guest и пяти auth проб, отдельно cold/warm, затем собственная upload/Reader проверка; остановка при identity/order/queue ошибке. Цель — устранить секундные штатные ответы; десятки миллисекунд SQL измерять отдельно от полной загрузки.

Подготовленный вариант, **ещё не выполнен**: дополнительный Render Frankfurt + изолированный Redis Frankfurt, dev-коммит Vercel `regions: ["fra1"]` и только dev Preview `API_URL` на новый бэк. Перед production-переключением: завершить или перенести задания обеих очередей, проверить текущие планы, persistence, диски, webhooks и фактическую стоимость второго сервиса.
