## 1. Разделить результат загрузки и доступность его проверки

Согласовано пользователем: отдельное состояние неизвестной готовности, действие проверки статуса, ошибка внутри прозрачной пунктирной обложки, дополнительное уведомление. Для коротких уведомлений новые модалки не нужны. Таблица описывает реализованный контракт; production frontend пока не обновляется.

| Ситуация | Постоянное отображение | Действие |
|---|---|---|
| Передача/обработка идут | Та же первая карточка, skeleton неизвестных полей; полученные metadata сохраняются | Закрыть модалку и пользоваться полкой; незавершённую книгу не открывать |
| Сервер подтвердил ошибку парсинга/сохранения | В области обложки прозрачная пунктирная рамка без заливки: «Не удалось обработать книгу». Реальный title, если известен; иначе конечный fallback | «Загрузить заново»; существующее удаление доступно для подтверждённо неудавшейся книги |
| Опрос не ответил / сеть / срок ожидания истёк | «Не удалось проверить готовность», нейтральная пунктирная рамка; без утверждения о провале EPUB и вечного skeleton | «Проверить статус» обращается к существующей попытке, не отправляет файл повторно |
| Ready, но порядок/обновление полки не подтверждены | Сохранить настоящую обложку и Reader; отдельно «Книга готова. Не удалось обновить полку» | «Обновить полку», не повторный импорт; порядок из следующего принятого manifest |
| Неизвестен результат передачи, job ID не получен / status сообщает not found | «Не удалось подтвердить загрузку»; отсутствие ответа не означает ошибку парсинга | Сначала обновить полку и сопоставить известную книгу/операцию; если подтвердить нельзя — явный выбор повторной загрузки с предупреждением о неизвестном результате |
| Книга готова, детали карточки ещё не получены | Сохранить canonical ID и готовность; заполнить доступные поля | Обновить сведения/полку, повторно файл не загружать |

Механизм: отдельные признаки server job, связи и подтверждения порядка; типизированные результаты/ошибки вместо классификации по тексту исключения. Поллинг с известным ID восстанавливает status после сетевой ошибки, а не создаёт новую попытку. `order_confirmed:false` не становится ошибкой содержимого. 401/403 идут в восстановление доступа, не в бесконечный retry или анонимный успех. Проверка статуса не меняет готовый контент, главы, прогресс и upload recency.

Точки изменения: `src/lib/api.ts` (`waitForBookJob`), `UploadBookModal.tsx`, MyBooks, BookCard, UploadBookPlaceholder и связанные DTO/hooks. Backend уже возвращает job state и `order_confirmed`; сначала использовать этот контракт. Если конкретному случаю не хватает машинного кода ошибки, выделить минимальное аддитивное изменение бэка после сверки с разработчицей. Новой миграции БД для реализованного UI не требуется.

## 2. Один компонент коротких уведомлений

Установлен `sonner@2.0.8`, общий `AppToaster` монтируется один раз в app layout. `src/lib/notifications.ts` задаёт scoped API; приложение не вызывает Sonner напрямую. Обёртка использует наши App semantic tokens, шрифт, радиусы, иконки и кнопки, библиотека отвечает за показ/закрытие/таймеры. [Контракт дизайн-системы](../../../reference/product/design-system.md#notifications) содержит правила и ограничения. Reader banner и IOS-диалоги сохранены; формы auth/billing не переписываются.

Основа — [Sonner из shadcn/ui](https://ui.shadcn.com/docs/components/radix/sonner). Scope handle включает поколение: A → B → A не оживляет старую операцию. Дедупликация событий действует в памяти текущей страницы, это не durable outbox. Максимум три активных сообщения; сообщение с фокусом не вытесняется новой операцией. При модалке сообщения подавляются, не копятся для показа после закрытия.

- Новые короткие события загрузки показываем общим компонентом. Постоянное состояние и восстановление остаются на карточке/баннере после исчезновения toast.
- Нижнее положение с учётом safe area, навигации и экранной клавиатуры; без прыжка фокуса. При открытой модалке ошибка и действие доступны внутри неё, а не за подложкой; второй одновременный toast не нужен.
- Одно сообщение на переход состояния операции, не на каждый двухсекундный poll, render или reload. Очередь ограничена; одинаковые события объединяются. Поздний ответ после удаления/смены аккаунта ничего не воскрешает, сообщения чужого scope очищаются.
- Реализован один native Sonner `polite` live-region для всех уровней; отдельного срочного/assertive API в этом выпуске нет. Не озвучивать одно событие в нескольких live-region. Сообщение с действием не исчезает во время hover/focus; путь восстановления сохраняется в постоянном UI.
- Длительность и тексты проверить на mobile/desktop в обеих темах. Успех каждого фонового poll не требует уведомления.
- Reader banner — ориентир существующего поведения. Перенос на общий примитив отдельно проверить с сохранением Try again/Reload chapter; не менять логику перевода. Все auth/billing формы ради унификации не переписывать.

## 3. Где добавить сообщения и действия

| Событие | Сообщение / восстановление | Ограничение |
|---|---|---|
| Ready при закрытой модалке | «Книга готова» → «Открыть» | Один раз для наблюдаемой попытки; не для старых книг при старте |
| Книга уже была на полке пользователя | «Книга уже в библиотеке. Прогресс сохранён» → «Открыть» | Global backend dedup не доказывает прежнюю принадлежность этому пользователю; если неизвестно — обычное «Книга готова» |
| Неизвестная готовность / подтверждённый провал | Разные сообщения и действия из таблицы выше | Не предлагать другой формат EPUB из-за сети/таймаута |
| Ready, но не обновилась полка | «Книга готова. Не удалось обновить полку» → «Обновить» | Сохранить доступ к книге |
| Удаление/архивирование/восстановление не удалось | Назвать действие → «Повторить» именно его | Optimistic rollback; неизвестный результат сначала сверить с сервером. Refresh не является повтором удаления |
| Истекла сессия / нет доступа | 401: «Войдите, чтобы продолжить» → вход с безопасным возвратом; 403: объяснить отсутствие доступа | Не стирать серверную книгу и не показывать чужой кеш |
| Соединение восстановилось после явной ошибки | Убрать устаревший offline banner; после ручной проверки «Библиотека обновлена» | Не показывать при каждом открытии или poll |
| Billing portal не открылся | Понятное сообщение с повтором | Пробел относится к billing backlog другого владельца, не к изменению оплаты в upload story |

Предупреждение о недоступности связи остаётся постоянным баннером, пока применимо. Ошибки валидации файла/формы остаются возле поля. Подтверждение удаления остаётся диалогом. Модалка загрузки отражает те же разрешённые действия, что полка: не оставлять активную повторную отправку при объявленном offline без проверки соединения.

## 4. Проверки и критерии приёмки

Начать с существующих upload/page/modal-race тестов и добавить проверки конкретных дефектов. После финальных frontend изменений: unit, соответствующие page/browser fixtures, TypeScript, scoped lint, production build. При изменении серверного контракта — его targeted/native проверки и сборка. Весь backend suite ради CSS не нужен; результаты прежнего выпуска не выдаём за проверку новой версии.

| Сценарий | Хорошо | Плохо / стоп выпуска |
|---|---|---|
| Timeout/500/network → processing → Ready | Проверка той же задачи, одна карточка, один итоговый toast | Неподтверждённый Upload failed, повторный upload по Check status, дубль |
| completed + order_confirmed:false + неудачный manifest | Книга доступна; отдельная ошибка полки; Refresh принимает актуальный серверный порядок; сам по себе не исправляет recency на сервере | Потеря Ready/обложки/Reader link, форматная подсказка, повторная передача |
| Неизвестен job ID / 404 / потерян ответ | Правдивый неизвестный результат, явный путь сверки/повтора | Ложное «не загрузилось» или бесконечная бесполезная кнопка Check status |
| Malformed EPUB / ошибка записи | Пунктирная обложка без фона, конечный текст, Upload again; тот же статус в модалке | Вечный skeleton или ложное Ready |
| Close/reopen modal, reload, повтор poll, 2 книги | Независимые попытки, уведомления без дублей, действия к нужной книге | Поздний ответ закрывает новую модалку, очередь toast растёт |
| Delete/archive/restore: отказ и потеря ответа | Rollback/сверка, повтор нужного действия | Retry просто обновляет список, удалённая карточка воскресает |
| Logout/account switch/401/403/late callback | Scoped уведомления сброшены, безопасный возврат после входа | Чужие сообщения/карточки, retry со старыми полномочиями |
| Dedup/готовый original/порядок | Один canonical ID, прежний прогресс/оригинал; status-check не поднимает recency | Потеря контента/позиции, ложное «уже на вашей полке» при global dedup |
| Mobile/desktop, темы, клавиатура, screen reader | Действие доступно, фокус не перехвачен, одно объявление | Toast под навигацией/модалкой, залитая error-cover, исчезновение при фокусе |

Ручная dev-проверка: собственные маленькие EPUB с отличающимся filename/title; success при закрытой модалке, malformed, повтор, Reader, восстановление связи, modal/offline consistency. Неизвестный результат и `order_confirmed:false` сначала воспроизвести управляемым transport на настоящей странице; искусственные сбои не выдавать за live production outage. Сохранить скриншоты и исходы новой версии, проверить фактический dev SHA. QA-объекты удалять только после проверки ownership. Боевые пользовательские книги для инъекций не использовать.

Локальные проверки доказывают переходы UI/DTO и заданные гонки, но не доступность Render/Supabase, память и реальные задержки. Dev использует общий backend/DB: облачные проверки должны быть малыми и предсказуемыми. В архиве backend **389 PASS / 11 FAIL** из-за отсутствующих EPUB fixtures: неполный suite, не зелёный результат и не новая регрессия этого плана.

## 5. Размер EPUB: ограниченное исследование

**Безопасный предел не измерен.** Parser fixtures до 6,15 MB сжатого файла не являются тестом ёмкости. Например, Nexus 5,67 MB содержит около 10,15 MB заявленных распакованных данных; DOM, число блоков и картинки влияют на память отдельно. Маленькие live QA EPUB проверяли корректность, не нагрузку.

На проверенном backend `ed7b30d` файл, DOM и массив блоков обрабатываются в памяти; вставка порциями по 1000 не ограничивает весь массив. Worker concurrency=2, API и worker делят процесс и 512 MB сервиса. Явный лимит EPUB/распакованного содержимого в проверенном коде не найден; облачный Storage limit не проверен. Старые Mac RSS-замеры baseline не доказывают ёмкость текущего Render.

Вопрос: сколько памяти/времени занимает текущая версия на четырёх имеющихся реальных fixtures и что меняют два одновременных импорта? Изолированная среда с сопоставимым лимитом памяти, без платных переводов/боевых данных. Сначала файлы по одному, затем одна пара только при запасе. Бюджет: четыре файла и максимум одна пара, не растущая серия огромных EPUB. Сохранить точные входы/версии, ZIP/unpacked размеры, peak RSS процесса, время до metadata/Ready и отклик API. Стоп: OOM/ошибка, приближение к лимиту (запас определить до запуска) или потеря отклика. Повтор только с новой гипотезой, adverse результат сохранить. По итогам выбрать ограничения/обработку памяти; пользовательский порог MB сейчас не выдумывать.

**Исключено пользователем:** отмена серверной обработки, надёжное распознавание DRM, новая инфраструктура долговечных upload tasks, приоритеты очереди обложек и отдельный проект поддержки старых frontend. Не возвращать их как обязательные защиты. Закрытие страницы во время передачи сохраняет ранее согласованное ограничение.

## Решения и ограничения реализации

- Завершённый первоначальный выпуск архивирован. Новые проверки записываются отдельно, прежние успехи не засчитываются новой версии.
- Неизвестная готовность отделена от подтверждённого провала. Ready + неподтверждённый порядок сохраняет Reader; ручной Refresh принимает текущий manifest и не обещает восстановить recency.
- Один Sonner host и API; постоянная карточка/баннер остаются после закрытия toast. Billing и Reader notification migration не входят в эту доработку.
- Review исправляет ложный успех Refresh при pending mutation, гонки auth-отказов, потерю фокуса при лимите toast и нормализацию metadata после bare completed job result. Регрессионные проверки содержат adverse исходы до исправлений.
- EPUB memory preflight: 4 точных fixtures инвентаризированы; 0 импортов/0 пар выполнено. На Mac нет работающего Linux/container runtime с 512 MiB cgroup. Протокол ограничен 4 singles + максимум 1 pair, стоп 448 MiB/ошибка/OOM/потеря отклика. Не переносить выводы Mac RSS на Render и не выдумывать безопасный порог MB.
- Backend 404 намеренно не различает отсутствующую/недоступную задачу. Без полученного ID результат может остаться неизвестным; UI сначала сверяет полку, затем предлагает явный повтор с предупреждением. Полная идемпотентность передачи не добавлена.
- Закрытие страницы во время передачи может прервать её. После reload обработка видна по manifest, но прежняя transient toast-история не восстанавливается.
