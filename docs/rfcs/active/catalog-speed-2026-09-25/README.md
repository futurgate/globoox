# План быстрого каталога — 25 сентября 2026

Цель: при входе быстро получить актуальные названия и порядок книг с сервера, затем заполнить карточки локальными данными и асинхронными обложками. При недоступности сервера — ограниченное ожидание, сохранённая библиотека своего аккаунта, уведомление и повтор. Корректность Recently Read между устройствами и после возврата из Reader входит в результат.

Реализация разрешена пользователем. Первое обязательное действие — до кода записать проверки, хорошие/плохие результаты и риски регрессий; матрица ниже добавлена перед изменением приложения. 26 сентября пользователь разрешил push/deploy бэка и миграцию рабочей БД после тестов при наличии отката; dev целиком переводится на новый frontend. Production frontend переключается после dev-приёмки. Детальный [контракт библиотеки](../../../reference/architecture/library-contract-as-is-to-be.md), прежде всего последние уточнения раздела 1, остаётся источником требований; безусловный cache-first и opt-in в старый `/api/books` не применяются. Уточнение 26 сентября допускает короткое повторное использование подтверждённого полного индекса по D14.

## Принятые ограничения

1. Новые маршруты, начиная с `GET /api/v2/library`; старые `/api/books` handlers, JSON/NDJSON и используемые другими клиентами write-контракты остаются без изменений. Новые service/helper файлы не должны незаметно менять legacy поведение.
2. В новом frontend один загрузчик каталога и один формат кеша. Нет постоянного feature flag между двумя API, runtime возврата к тяжёлому legacy списку или параллельных сортировщиков. Dev целиком переходит на новый frontend; после его приёмки production целиком переходит на новый frontend.
3. В пределах короткого кулдауна D14 допустим сразу полный недавно подтверждённый индекс своего scope. Вне этого исключения на входе сначала skeleton; кеш виден при timeout/сетевом сбое. После успешного ответа локальные изображения заполняют подтверждённые сервером карточки. Временный placeholder собственной текущей загрузки по D13 не означает подтверждение полного индекса.
4. Сервер определяет разрешённый набор и порядок. Возврат из Reader не публикует индекс, который ещё не учитывает предшествующее чтение/мутацию этого клиента. Нужен ack или эквивалентная гарантия read-your-writes в пределах общего срока ожидания.
5. Оригинальные книги, обложки, несинхронизированные позиции, пользовательские данные и legacy поля не удаляются. Подготовка thumbnails и возможные новые поля/таблицы аддитивны. Не выполнять blanket reset IndexedDB/localStorage.
6. Длинные snapshot-сессии, новый общий offline sync engine и пагинация не являются обязательным стартовым объёмом. Выбирать их только для измеренной проблемы; минимальная обработка pending reading activity обязательна до переключения frontend.

## Этап 0. Ограничить критический путь и выбрать масштаб

Вопрос: сколько нового ожидания создают identity, БД, сериализация, proxy и собственно передача компактных данных? Снять отдельные timings прямого backend и полного browser → proxy → backend пути в согласованной тестовой среде. Проверить установленную схему/индексы, effective visibility и все источники recency; исходники миграции не доказывают её применение.

Начать с guest, обычного authenticated аккаунта и библиотеки большего размера. Зафиксировать scope без токенов, число книг, сеть/устройство, cold/warm, ошибки, размер ответа, время названий и реально показанных обложек. Не собирать private titles/содержимое книг в общие логи.

**Первый вариант — полный компактный manifest:** все разрешённые ID, названия/авторы, effective status/права, canonical recency и thumbnail references/versions, без изображений и глав. Полнота ответа явная; одна согласованная server projection задаёт порядок. Не наследовать нынешний recency-head + created-at-tail. Для обычного размера такой ответ проще cursor/snapshot инфраструктуры. Рендер первых шести и загрузка их картинок не ждут картинок остальных книг.

Предварительная граница проверки — 1000 книг и не более 512 KiB декодированного manifest. Это экспериментальный предел, не установленный лимит продукта: проверить также реальный крупный аккаунт, если он доступен. Если полный manifest укладывается в бюджет, сохранить его и клиентскую работу по полному набору для поддерживаемых фильтров/поиска. Если превышает размер или время, назвать конкретную причину и перейти к серверным sort/filter/limit; не обрезать массив без continuation. Не грузить все cover blobs или все тяжёлые metadata в Node ради отбора первых книг.

Ожидаемое доказательство: короткая таблица timings/bytes, план SQL/EXPLAIN на тестовых данных и выбранная стратегия перечисления. Бюджет: до 3 диагностических запросов на каждый из 3 scopes; для проверки масштаба одна изолированная fixture-библиотека на 1000 книг и один диагностический SQL plan. При auth/schema blocker остановить соответствующее измерение, не заменять его гостевым результатом. Не создавать массовые production записи ради benchmark.

## Этап 1. Новый компактный серверный путь

- Новый route/service и отдельный frontend proxy route. Explicit account/share context обязателен: существующий share helper работает только с префиксом `/api/books`. Подтвердить principal; не выдавать guest success вместо ожидаемой пользовательской библиотеки.
- Новый DTO явно задаёт contract version, scope/query context, revision, полноту и items. В SELECT и wire payload нет оригинального base64. Название/автор, ID, effective status, права и данные порядка доступны без дополнительных запросов; reading summary batch/join допускает unknown, если честный процент недоступен. Не вызывать N reading-position GET ради карточек.
- Глобальный Recently Read сортируется до выбора head/страницы: каноническая recency, затем deterministic ties. Выбрать и проверить null/unread правило, created_at/ID tie-break и title collation. Legacy language PATCH и старые writers сейчас загрязняют last_read_at: простое переименование поля не создаёт событие чтения.
- При полном manifest один запрос получает согласованный набор; если серверные чтения составные, проверить отсутствие смеси разных membership/order состояний. Revision — сигнал изменения, не обещание исторического snapshot. Не заводить хранение snapshot-сессий для одного малого ответа.
- При обоснованной пагинации сервер применяет доступ, visibility, поиск и выбранную сортировку ко всему набору до limit. Cursor привязан к scope/query. До выпуска выбрать фиксированное перечисление либо обнаружение смены revision с явным restart; второе не называть snapshot. Не смешивать страницы разных revision; partial cache не обозначать полной библиотекой.

Выход этапа: новый endpoint отдаёт лёгкий корректный индекс; unchanged legacy запросы дают прежний контракт. Это подготовка, ещё не законченный пользовательский путь.

## Этап 2. Подтверждённое чтение и отдельные thumbnails

**Reader → Library:** определить минимальное новое activity событие реального готового Reader/чтения и добавить отдельный write endpoint, если существующих подтверждений недостаточно. Event ID, scope и исходное время сохраняются до ack; повтор не создаёт новое чтение. До показа индекса дождаться ack влияющих на него действий и читать не старше подтверждённой версии, либо получить равнозначную атомарную операцию. Барьер входит в общий timeout. Failed/delayed ack ведёт к scoped fallback с pending локальным порядком; более старый server order не показывается как промежуточный успех.

Не превращать position conflict в максимум номера страницы: чтение назад допустимо. Существующее `persisted:false` остаётся отличимым от успешного HTTP. Новое событие чтения и версия позиции — разные сущности. До переключения принять конкретную политику часов, delayed offline событий и logout; хотя общий offline engine отложен, pending activity не должна бесследно теряться при перезагрузке. Не обещать replay всех offline мутаций, которых текущий клиент не умеет доставлять.

Для двух устройств новый канонический порядок строится из одного серверного источника. Проверить всех legacy writers и выбрать совместимую projection/дополнительное поле, не изменяя старые handlers и общую семантику молча. Старые last_read_at без provenance можно использовать только как явно обозначенное legacy приближение; историческое реальное чтение из них не восстановить. Зафиксировать границу строгих гарантий для нового и legacy клиента до реализации.

**Обложки:** новый import/backfill шаг создаёт маленький thumbnail и хранит размер/version отдельно от оригинала; list GET ничего не декодирует и не ресайзит. Backfill возобновляемый и ограниченный, с первоначальной пробой на 6 книгах. До больших записей оценить свободное место, рост и сохранность оригиналов. Отсутствие thumbnail не блокирует названия: отдельный разрешённый image URL/placeholder — переходный вариант, но передача оригиналов не считается достижением thumbnail бюджета.

Private image endpoint/signed URL сохраняет доступ; public bucket не является универсальным решением. Ключ изображения — scope + book ID + thumbnail version. Истечение URL обновляет доступ к картинке, а не меняет весь каталог. Декодирование/ошибка изображения не меняет порядок и не переводит всю библиотеку в offline. Обложки догружаются самостоятельной ограниченной FIFO-очередью сверху вниз в порядке полки. Приоритеты и перестановки по viewport исключены пользователем; скролл не запускает и не переупорядочивает сетевую очередь. Готовый ответ заполняет свой слот независимо от завершения предыдущих картинок.

| 401/403, другой principal, отсутствующий v2 или неверный DTO | Отдельная auth/access/deployment ошибка; не маскировать под отсутствие интернета и не запрашивать legacy список. |
| Тот же принятый индекс / ошибка одной картинки | Сохранить карточки по book ID; не показывать повторно общий skeleton. |

Автоматическая перестановка fallback после позднего запроса не согласована; возвращение к актуальному набору выполняется успешной отдельной повторной попыткой. Постоянный индикатор режима/Retry, дополняющий toast, остаётся предложением оформления, а не новым утверждённым требованием.

Cache migration выполняется один раз: пригодный старый scoped список преобразуется в новый emergency cache без сетевого legacy fallback. Если ownership/формат не подтверждается, не переносить его наугад. Не удалять сохранённые тексты, картинки, anchors и pending writes. Новые keys учитывают account/guest/share, query и completeness. Logout/смена scope исключают чужие данные, а delete/archive не откатываются поздним list GET или старой страницей. Ограничения offline Reader/действий показывают только реально доступные функции.

Свежесть проверяется на входе/возврате с коротким исключением D14; старый пятиминутный shortcut не возвращается. Conditional GET/304 — последующая оптимизация того же пути: только после корректной invalidation recency/prefs/public/share изменений. До 304 сервер подтверждает актуальность точного scoped/query кеша; тело после 304 используется лишь при наличии соответствующего полного ответа. Сохранить legacy `/sync/status` даты и EPUB binary/Content-Disposition поддержку proxy, пришедшую из main.

## Следующая итерация после обсуждения 26 сентября

1. Кулдаун D14: проверить повтор на 5 с и границу 10 с, истечение срока, reload, разные аккаунты/share, пустой полный индекс, storage failure/скачок часов, отсутствие продления срока от повторного чтения кеша; чтение и все изменения полки должны отменять reuse. Нельзя использовать savedAt локального ACK как подтверждение всего списка.
2. FIFO D12: без скролла загрузить больше одного экранного набора, не более четырёх активных запросов, стабильные слоты при разном времени ответов, пропуск уже сохранённых версий, изоляция ошибки одной обложки, отмена чужого scope. Таймаут запроса начинается после получения места в очереди, а не во время ожидания.
3. Placeholder D13: появляется сверху сразу при начале загрузки и виден под модалкой; имя файла до готового названия, статусы «Загружается/Обрабатывается/Ошибка». По успеху тот же элемент наполняется без дубля и без 1,5-секундной паузы; повторно открытая модалка не должна закрываться callback старой попытки. Проверить ошибку, dedup в существующую книгу и закрытие только модалки. Долговечное восстановление после закрытия страницы не входит в приёмку. Локальная карточка не выдаётся за подтверждённый полный серверный кеш; обычный серверный порядок применяется при следующем входе.
4. После локальной проверки — реальная интеграция и ограниченный сравнительный benchmark по исходным бюджетам. Текущие размеры и SQL timing не заменяют время первого экрана в браузере.

Контрольный профиль: mobile browser, RTT 100 мс, 10 Mbit/s, одинаковая среда до/после; отдельно cold auth/новая вкладка, warm и Reader return. ## Как проверяем: хороший и плохой результат

**Хороший результат:** все обязательные проверки корректности ниже прошли; старые серверные handlers сохранены; полный новый путь реально показывает нужные названия и обложки в заявленных бюджетах. Сравнимый cold median должен ускориться хотя бы вдвое против baseline; p95 также должен укладываться в цели выше. Это критерий приёмки, не уже полученный результат. **Плохой результат:** любое нарушение identity/данных/порядка, потеря pending события, скрытая неполнота списка, повторная публикация устаревшей попытки; либо ускорение только пустого skeleton/текста при медленных обложках. Превышение performance budget или неподтверждённое реальное поведение означает «нужно доработать/проверить», а не PASS.

Синтетические проверки доказывают только заданные сценарии. Отсутствующая authenticated/cross-device или реальная performance проверка явно остаётся NOT RUN и блокирует утверждение о готовности выпуска; guest/mock нельзя подставлять вместо неё. При изменении бюджета сначала записать измеренную причину/компромисс в D06; не ослаблять критерий только ради зелёного отчёта.

## Порядок внедрения

1. Проверенная локально аддитивная миграция нужна для внедрения. Перед применением сверить установленную схему и SQL-канал, затем применить миграцию к рабочей Supabase и развернуть backend с новыми маршрутами. Рабочая БД не используется для экспериментальных схем и массовых fixture-записей.
2. Dev целиком перевести на новый frontend. На нём проверить server-first, кулдаун, FIFO-обложки, upload-placeholder, Reader ACK, identity, кеш, мутации и два устройства с новой версией. Сценарии смешанных frontend-версий исключены из приёмки.
3. После успешной dev-приёмки production целиком перевести на новый frontend; подтвердить endpoint/schema/deployment версии и повторить небольшой smoke. Push/deploy бэка и рабочая миграция разрешены пользователем при пройденных тестах и проверенном откате. Выполнение отслеживается в таблице текущего состояния.
4. Сохранить книги, обложки, позиции и pending данные. Старые серверные ручки остаются неизменными по исходному требованию; это не означает отдельную программу поддержки или проверки смешанных frontend-версий.

Причины: Render Oregon, Vercel iad1, Supabase Ireland; последовательные remote auth/RPC, иногда дополнительно блокирующий track-IP. Вопрос следующего эксперимента: насколько размещение backend в Европе сокращает usable-index без изменения membership/auth семантики. До пяти guest и пяти auth проб, отдельно cold/warm, затем собственная upload/Reader проверка; остановка при identity/order/queue ошибке. Цель — устранить секундные штатные ответы; десятки миллисекунд SQL измерять отдельно от полной загрузки.

Подготовленный вариант, **ещё не выполнен**: дополнительный Render Frankfurt + изолированный Redis Frankfurt, dev-коммит Vercel `regions: ["fra1"]` и только dev Preview `API_URL` на новый бэк. Старый Oregon остаётся для отката. Регион существующего Render сервиса неизменяем; его внутренний `REDIS_URL` между регионами не работает. Два автоматически запускаемых BullMQ worker (`epub-processing`, `cost-measure`) означают, что новый backend нельзя без проверки подключать к действующей очереди. Перед production-переключением: завершить или перенести задания обеих очередей, проверить текущие планы, persistence, диски, webhooks и фактическую стоимость второго сервиса. Развёртывание второго платного комплекта и переключение регионов не выполнялись.

Панель Render проверена: действующий backend Starter — 0,5 CPU / 512 MB, $7/мес, 1 instance. Redis — Free, 25 MB / 50 connections, persistence Off, allkeys-lru. Подготовленный отдельный европейский тестовый комплект: backend $7 + Key Value 256 MB $10 = **дополнительно $17/мес за время параллельной работы**, без переменного usage/налогов. Новые платные сервисы не созданы; перед созданием требуется согласовать дополнительные расходы.
